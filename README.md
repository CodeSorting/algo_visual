# STRINGS LAB · KMP vs Rabin–Karp

같은 문자열 검색 문제를 푸는 두 알고리즘의 **내부 동작**을 단계별로 비교하는 주제 A 시각화 웹사이트입니다. KMP의 LPS 테이블 구성과 불일치 후 재사용, Rabin–Karp의 롤링 해시와 해시 일치 후 실제 문자 검증을 살펴봅니다.

별도 설치나 빌드가 필요 없는 HTML·CSS·JavaScript 프로젝트입니다. 이 폴더의 `index.html`을 브라우저에서 열면 로컬에서도 사용할 수 있습니다. 이 패키지를 만드는 작업만으로 기존 GitHub 사이트가 변경되지는 않습니다.

## 실행 방법

1. 압축 파일을 풀고 `index.html`을 엽니다.
2. 본문 문자열 T와 패턴 P를 입력하거나 예제를 선택합니다. 두 입력은 각각 Unicode 코드 포인트 기준 1~10자입니다. 인덱스는 0부터 시작하며, 대소문자와 공백을 구분합니다.
3. KMP 또는 Rabin–Karp를 선택하고 이전·다음 단계로 이동합니다. 재생, 처음으로 돌아가기, 속도 조절, 타임라인으로 실행 과정을 탐색할 수 있습니다.
4. 주요 동작으로 이동하는 버튼을 이용해 LPS 재사용, 해시 갱신, 일치·충돌 장면을 확인합니다.
5. 현재 단계 그림은 SVG, 실행 기록은 JSON으로 저장할 수 있습니다. 인쇄는 브라우저의 인쇄 기능을 이용합니다.

알고리즘별 단계 수는 교육용으로 동작을 나눈 수입니다. 실행 시간이나 속도 배율을 나타내지 않습니다.

## 권장 예제

| 예제 | 본문 T | 패턴 P | 살펴볼 동작 |
| --- | --- | --- | --- |
| 기본 | `ABABCABAB` | `ABAB` | 정답 `[0, 5]`, LPS `[0, 0, 1, 2]` |
| 반복 문자 | `AAAAAAAAAB` | `AAAAB` | 반복되는 접두부의 재사용 |
| 겹치는 정답 | `ABABABABA` | `ABA` | 정답 `[0, 2, 4, 6]`을 모두 찾기 |
| 해시 충돌 | `AGAB` | `AB` | q=5에서 `AG`와 `GA`를 거절하고 인덱스 2만 정답으로 기록 |
| 검색 실패 | `ABCDEABCDE` | `XYZ` | 일치 항목 없이 검색 종료 |
| 한글 | `가나다가나` | `가나` | 정답 `[0, 3]`, 코드 포인트 기준 인덱스 |

Rabin–Karp의 기본 설정은 b=256, q=101이고 충돌 예제는 q=5입니다. 문자의 값은 `codePointAt(0)`으로 얻습니다. 해시 충돌이 발생해도 실제 문자를 확인하므로 오답을 기록하지 않습니다.

## GitHub Pages에 올리기

### 기존 `algo_visual` 저장소 교체

기존 N-Queens 버전을 보관하려면 먼저 저장소를 ZIP으로 내려받거나 Git 커밋을 남깁니다.

1. GitHub에서 `codesorting/algo_visual` 저장소를 엽니다.
2. **Add file → Upload files**를 선택합니다.
3. 이 폴더 안의 파일들을 저장소 최상위에 올리고 커밋합니다. `kmp-rabin-karp` 폴더 자체가 한 단계 안쪽으로 들어가지 않도록 합니다. 최상위의 `index.html`, `styles.css`, `app.js`, `algorithms.js`가 함께 있어야 합니다.
4. **Settings → Pages → Build and deployment**에서 **Deploy from a branch**, 브랜치 **main**, 폴더 **/(root)**를 선택하고 저장합니다. 기존 설정이 같으면 유지합니다.
5. GitHub의 배포가 완료된 뒤 [기존 사이트 주소](https://codesorting.github.io/algo_visual/)를 열어 제목이 새 주제로 바뀌었는지 확인합니다. 이전 화면이 보이면 새로고침하거나 잠시 후 다시 확인합니다.

웹 업로드에서 `.nojekyll` 같은 숨김 파일을 선택하기 어렵다면 빠져도 이 프로젝트의 기본 화면은 동작합니다. 이 프로젝트에는 Jekyll 처리에 필요한 파일이나 빌드 단계가 없습니다.

### 새 저장소 사용

새 공개 저장소를 만든 뒤 같은 파일을 최상위에 업로드하고 Pages의 `main` / `/(root)` 배포를 설정합니다. 주소는 GitHub Pages가 표시하는 실제 URL을 사용합니다. 저장소 이름에 따라 기존 주소와 달라집니다.

보고서에 웹 주소를 적는 경우 새 버전이 실제로 열리는지 확인한 뒤 반영합니다. 제출 PDF 자체에도 핵심 동작 그림과 설명이 포함되어 있으므로 웹 링크에만 의존하지 않습니다.

## 집계와 복잡도를 읽는 기준

- **전처리 문자 비교**: KMP가 LPS를 만들 때 수행한 문자 동등성 비교입니다.
- **검색 문자 비교**: KMP의 본문·패턴 비교 또는 Rabin–Karp의 해시 일치 후보 검증에서 수행한 문자 비교입니다.
- **해시 비교**: Rabin–Karp가 현재 창의 해시와 패턴 해시를 비교한 횟수입니다.
- **해시 갱신**: 창을 한 칸 옮기면서 이전 해시에서 다음 해시를 계산한 횟수입니다.
- **충돌**: 두 해시가 같지만 실제 문자열이 달라 거절한 후보 수입니다.

서로 다른 종류의 연산을 합산해 하나의 속도 점수로 비교하지 않습니다. 해시 계산에도 산술 연산이 필요하며, 실제 실행 시간은 입력과 실행 환경의 영향을 받습니다.

n은 본문 길이, m은 패턴 길이, v는 실제 정답과 충돌을 모두 포함한 해시 일치 후보 수입니다. 이 구현은 첫 정답에서 종료하지 않고 겹치는 정답까지 모두 찾습니다.

| 기준 | KMP · LPS 방식 | Rabin–Karp · 문자 검증 방식 |
| --- | --- | --- |
| 시간 | O(n+m) | O(n+m+v·m), 최악 O(nm) |
| 이유 | LPS 전처리 O(m), 검색 중 본문 인덱스가 뒤로 가지 않음 | 최초 해시 O(m), 창 이동 O(1), 해시 일치 후보마다 최대 m자 검증 |
| 핵심 작업 공간 | O(m) | O(1) |

공간 표는 입력과 정답 목록을 제외한 핵심 알고리즘의 작업 공간입니다. 웹사이트가 Unicode 처리를 위해 만드는 문자 배열과 되돌아보기를 위해 저장하는 단계별 기록은 별도입니다.

검증할 문자의 총량이 O(n+m)이 되는 조건에서는 Rabin–Karp의 전체 시간도 O(n+m)입니다. 이 사이트는 재현하기 쉬운 고정 q를 사용하므로 기대 선형 시간을 무조건 보장한다고 설명하지 않습니다. 충돌이 없어도 겹치는 실제 정답이 매우 많으면 모든 정답을 문자로 재검증하는 비용이 커질 수 있습니다.

## 알고리즘 검증

Node.js가 설치된 환경에서 이 폴더를 작업 디렉터리로 열고 실행합니다.

```sh
node --test tests/algorithms.test.cjs
```

검증은 독립적인 문자열 검색 정답과의 대조, 겹치는 일치, 검색 실패, Unicode 입력, 롤링 해시의 재계산 일치, 의도적인 해시 충돌을 포함합니다. 실행한 환경에서의 실제 통과 여부는 명령 결과로 확인할 수 있습니다.

## 참고와 AI 활용

- [Princeton Algorithms, 4th Edition · Substring Search](https://algs4.cs.princeton.edu/53substring/)
- [Princeton · Substring Search 강의 자료](https://algs4.cs.princeton.edu/lectures/keynote/53SubstringSearch-2x2.pdf)

KMP는 LPS를 사용하는 구현입니다. 참고 자료의 전체 DFA 방식에서 사용하는 O(mR) 공간과 구분합니다. Rabin–Karp는 해시 일치 후 문자를 확인하는 방식을 구현했습니다.

AI 도구를 웹사이트 코드, 설명 초안, 보고서 구성 및 검증 작업에 활용했습니다. 제출 전에는 각 단계와 복잡도 설명을 직접 확인하고 자신의 말로 설명할 수 있는지 점검해야 합니다.
